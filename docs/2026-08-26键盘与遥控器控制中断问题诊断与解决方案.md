# 键盘与遥控器控制中断问题复盘与修复方案

日期：2026-08-26  
依据会话：`01a03d0c-5bee-74a2-8c29-cf637fa72083` 及本轮人工复测  
基准版本：`7492ccf`（阶段 5：runSim 5.0.2 收尾）  
当前结论：现有实验性修复未解决现场问题，应退回 5.0.2 已验证控制语义后做窄修复

## 1. 用户确认的基线事实

5.0.2 发行时的实际状态是：

1. 键盘按住时可以连续控制，不存在当前“运行不到 1 秒又停车、松开后又短暂运动”的问题。
2. 实时点阵云尚未启用。
3. 遥控器接近高端约 `1772`（现场也可能在更小值）会停车。

因此，当前键盘和遥控器同时断续不能被解释为 5.0.2 遗留的同一个问题。正确分类是：

- 遥控器极值停车：5.0.2 已知边界缺陷；
- 键盘连续性损坏：5.0.2 之后的实验性控制链改造造成的回归；
- 实时点云：独立功能需求，只能修改遥测和显示路径，不能以重写驾驶链为代价启用。

## 2. 本轮现场证据

### 2.1 当前修复仍然失败

人工同时复测键盘和遥控器后，用户确认“问题完全没有解决”。本轮 CSV 在 46 秒内记录到几十段目标轮速归零，其中多段持续 `0.1–3.5 s`，不是单帧显示抖动。

因此，此前“局部自动化测试通过”的结论不能升级为现场修复成功。

### 2.2 relay 与 command receiver 不是本轮已证实的断点

无缓冲开发诊断观测到：

- relay 最大实际发送间隔约 `44.8 ms`；
- C++ 最终租约为 `100 ms`；
- receiver 持续报告 `accepted=True`；
- authority 持续为 `ACTIVE`；
- eCAL command peer 数为 1。

这组数据否定了“本轮仍失败一定是 relay 被 GIL 阻塞超过 100 ms”的判断。历史上曾观察到 `131.3 ms` 间隔，只能证明旧线程方案在某次负载下有风险，不能解释本轮 relay 已稳定时仍出现的零命令。

### 2.3 遥控器硬件和原始串口数据稳定

唯一合格端口为：

```text
/dev/serial/by-id/usb-FTDI_Quad_RS232-HS-if02-port0
```

脱离仿真进行 15 秒只读采样：

```text
frames=1490
CH1 min/max=1002/1002
CH3 min/max=1099/1109
```

固定杆位期间 CH3 没有跳回中位 `1002`，帧率约 100 Hz。完整程序中却出现：

```text
moving=True → moving=False → moving=True
parser_desynchronized
```

所以硬件、FTDI 端口和原始字节流不是当前断续的首要嫌疑；零命令是在当前生产解析、仲裁或其后的实验性链路中产生的。

### 2.4 当前工作树已偏离 5.0.2 控制链

当前 `HEAD` 本身就是 5.0.2 收尾版本；问题代码主要位于尚未提交的工作树改动。相对 `7492ccf`，控制相关范围约新增 1114 行、删除 152 行，并引入：

- `KeyboardEventTracker`；
- 独立 `RunSimCommandRelayClient`；
- 独立 `RunSimCommandReceiver`；
- Dashboard command observer 转接；
- shared-array latest-only mailbox；
- 多组诊断和新的进程生命周期。

这些改动远大于“启用实时点云 + 修正 RC 极值”的需求边界。多次局部 GREEN、人工仍失败说明不能继续在这条实验链上叠加补丁。

### 2.5 X11 闪退是独立故障

本轮还复现了：

```text
The X11 connection broke: I/O error (code 1)
XIO: fatal IO error 62 (Timer expired) on X server ":1"
```

这会使程序退出，但不能解释窗口仍存活时周期性的运动—停车。后续验收必须分别记录“进程退出”和“控制插零”，禁止混成一个根因。

## 3. 对旧诊断的修正

下列说法现已证据不足或被现场否定：

1. **当前故障已经由独立 relay/receiver 修复。** 人工复测失败，结论撤销。
2. **当前断续仍由 relay 超过 100 ms 引起。** 本轮最大约 `44.8 ms`，不足以支持该结论。
3. **5.0.2 的键盘本来就存在相同问题。** 用户明确确认 5.0.2 键盘连续正常。
4. **遥控器本身回中或串口断帧。** 1490 帧只读样本不支持该判断。
5. **只要把所有 SBUS 通道范围扩大到 `172–1811` 即可。** 这虽然容纳极值，却扩大了错误对齐字节被当成合法帧的概率；完整程序已经出现 `parser_desynchronized`，需要结构化重同步测试后才能采用。
6. **自动化窗口注入等同人工按键。** X11 自动重复、焦点与人工操作时序不同，自动输入只能辅助定位，不能替代人工门禁。

## 4. 根因分层

### 4.1 已确认：修复范围失控导致控制回归风险

5.0.2 已验证的键盘输入、单进程 command 接收和命令应用语义被同时改动，而实时点云需求本不要求修改这些路径。当前回归首先应归因于这批未提交实验性控制改造，而不是继续假设 5.0.2 基础架构错误。

### 4.2 已确认：RC 极值校验混淆协议范围与实机校准范围

5.0.2 使用：

```text
通道合法范围：282–1772
实机校准点：282 / 1002 / 1722
```

当控制通道超过旧合法上限时，整帧会被拒绝并触发安全停车。协议合法性与操纵杆映射校准不应共用同一范围。

但修复不能简单放宽全部 16 个通道后结束；解析器还必须验证帧结构、跨 read 残留和错位重同步，确保数据区内偶然出现的 `0x0F` 不会成为假帧头。

### 4.3 待二分确认：当前键盘插零的最小引入点

当前至少有三组同时变化：

1. 无状态 `command_from_keyboard()` 改为 `KeyboardEventTracker`；
2. 直接 command client 改为进程 relay；
3. 进程内 eCAL command callback 改为 receiver sidecar。

由于三组变化在同一工作树叠加，现有 trace 不能诚实地把键盘回归唯一归到其中一个类。应从 5.0.2 基线逐项恢复，每次只加入一个必要变化并做人工长按门禁。

## 5. 修复原则

1. 以 `7492ccf` 的键盘连续行为为不可回退基线。
2. 实时点云仅修改 LiDAR 接收、缓存、降采样、后台渲染和 GUI 提交，不修改 keyboard、arbiter、Command socket 或 wheel decision。
3. RC 只修协议边界和帧重同步，不重写控制源仲裁。
4. C++ `100 ms` 安全租约保持不变。
5. 每次只引入一个行为变化，执行 RED → GREEN → 相关回归 → 人工实机验证。
6. 人工验证失败时立即回到最近一个通过的快照，不再叠加新假设。

## 6. 分阶段修复方案

### 阶段 A：恢复 5.0.2 控制语义

从当前工作树中移除或隔离所有尚未证明必要的控制实验层：

- PyBullet 键盘恢复 5.0.2 的直接 `command_from_keyboard(p.getKeyboardEvents())` 路径；
- command 接收恢复 5.0.2 的既有订阅和 wheel decision 路径；
- 暂不让 Dashboard 点云观察者改变 command subscriber 所有权；
- 保留诊断输出，但诊断不得改变线程、进程、订阅数量和控制时序；
- RC 暂时使用 5.0.2 解析器，以中等杆位验证连续性。

验收：关闭实时点云时，PyBullet ↑ 和 Dashboard W 各持续 30 秒，目标轮速不得插零；RC 固定中等杆位 30 秒不得插零。

### 阶段 B：窄修 RC 极值

先写真实字节流回归：

1. CH1/CH3 在 `172`、`282`、`1722`、`1772`、`1811` 均可解析。
2. 控制通道超出校准点后饱和到 ±1，不停车。
3. 固定 `1811` 以 100 Hz 连续 30 秒，输出不能插零。
4. 在数据区插入 `0x0F`、前缀噪声、缺字节和粘连帧，解析器只能输出结构完整的真实帧。
5. 非控制通道的合法范围依据真实设备样本确定，不用一个未经验证的全局范围掩盖错位。
6. 真正损坏、失联和超时仍 fail-closed。

实现优先级：先增加可靠帧边界判据和重同步，再分离“协议合法范围”与“CH1/CH3 校准范围”。

### 阶段 C：独立启用实时点云

实时点云只能在以下边界内实现：

- eCAL LiDAR 接收与 command 接收互不持有对方锁；
- 点云 mailbox 容量为 1，只保留最新帧；
- 点云转换和绘图位于后台 worker；
- GUI 主线程只提交已完成的 pixmap；
- 限制渲染频率和最大显示点数；
- 点云关闭时不得创建额外 command subscriber 或控制 relay。

验收顺序：

1. 阶段 A/B 控制门禁在点云关闭时通过；
2. 只打开点云接收、不渲染，重复控制门禁；
3. 打开降采样渲染，重复控制门禁；
4. 若首次失败，用该单一增量定位，不修改控制语义规避。

### 阶段 D：仅在证据要求时隔离续租

如果阶段 C 的同一快照实测再次出现 command socket 续租间隔 `>=100 ms`，才引入最小独立续租进程。该进程必须：

- 只拥有 Command socket；
- 使用容量 1 的最新目标；
- 不拥有 eCAL subscriber、Dashboard 或点云数据；
- 父进程退出、管道 EOF 或 generation 切换时立即安全归零；
- 在启用前后使用同一人工操作重放验证。

不提前引入独立 receiver sidecar；只有确认 5.0.2 的 command callback 在点云负载下发生接收龄超时，才单独评估。

## 7. 必须补齐的自动化门禁

### 7.1 键盘

- 重放 5.0.2 真实 PyBullet flags，确认持续 `KEY_IS_DOWN` 时不插零。
- 真正 release 后在合同时间内归零。
- Dashboard Qt 自动重复 release 不清除 `_pressed_keys`。
- `manual_demo → arbiter → command client` 跨层测试必须断言整个持有窗口无零目标。

### 7.2 遥控器

- 使用实机捕获的原始 25 字节帧作为 fixture，而不只用测试自造帧。
- 覆盖端点、噪声、错位、分段 read、连续 30 秒和回中。
- 每次 parser 丢帧必须带结构化原因和原始 CH1/CH3 诊断。

### 7.3 验收器

正式 v2 CSV 中 `command_linear_velocity` 按设计为零，验收器必须读取：

```text
left_target_drive_speed
right_target_drive_speed
```

通过标准是第一次非零到最后一次非零之间不存在意外双轮零速，而不是只看位移或 `command_linear_velocity`。

## 8. 人工实机验收

每次启动后由用户手动操作，测试进程保持运行，诊断实时输出，不使用自动注键替代最终结论。

### 键盘

1. 明确选择键盘源。
2. PyBullet 窗口持续按住 ↑ 30 秒。
3. Dashboard 窗口持续按住 W 30 秒。
4. 分别测试松开、反向和转向。
5. 持有区间内左右目标轮速不得同时归零；松开后不得继续重放旧目标。

### 遥控器

1. 明确选择 RC 源。
2. 中等非零杆位保持 30 秒。
3. 缓慢越过 1722/1772，接近实机极值保持 30 秒。
4. 全程记录 CH1、CH3、parser 状态、watchdog、arbiter 目标和最终轮速。
5. 合法极值不得触发 `parser_desynchronized`；回中后应稳定归零。

### 启动稳定性

单独运行 5 分钟窗口稳定性测试，记录 X11 断开时间、PyBullet 退出码和 DISPLAY 状态。X11 闪退未解决时，不得用控制测试进程退出代替控制连续性结论。

## 9. 当前交付判定

当前准确状态是：

> 旧诊断中的实验性修复已被人工测试否定；已重新锁定 5.0.2 为已知良好控制基线，并确认遥控器原始串口稳定。下一步应恢复 5.0.2 控制语义、窄修 RC 极值，再把实时点云作为独立增量启用。

在键盘、遥控器和实时点云三阶段人工门禁全部通过前，不得声明问题已解决。
