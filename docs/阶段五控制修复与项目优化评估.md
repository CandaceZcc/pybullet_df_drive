# 阶段五控制修复与项目优化评估

> 已被 5.0.2 控制合同取代：本文保留 CH6 门限修复的历史证据，但当前实现已完全移除 CH6/解锁/自锁，改为 50 Hz latest-target mailbox、200 ms 软停车、硬故障立即停车和连续 3 帧自动恢复。当前用法以 `README.md` 为准。

日期：2026-08-21
项目：PyBullet 3D 移动机器人仿真平台

## 1. 结论

本次完成两项直接修复：

1. 修复选择遥控器后，遥控器未解锁且键盘也无法接管的问题。
2. 将 Dashboard 的折线图标签改为按需选择，默认不创建图表；取消选择后同步释放绘图对象、回调和历史缓存。

控制故障的根因不是车辆执行器失效，而是遥控器 CH6 实际档位范围与旧解锁门限不匹配。遥控器无法解锁时，控制仲裁器会撤销 RC 控制权；但 Dashboard 仍停留在“遥控器”选项，键盘因此也不能接管，最终表现为两个输入源都无法控制车辆。

修复后，RC 未解锁、串口超时或数据故障时，Dashboard 会自动退回键盘。遥控器通过 CH6 低位到高位的安全解锁后，仍可由用户主动选择并接管车辆。

2026-08-24 的补充收口还修复了正式 v2 Dashboard 的两个回归：MID-360 OpenGL 视图改为独占一整行，控制、状态与诊断统一放在下一行；点云工作台折叠时不再向控制主线程提交 OpenGL，打开时每个可见帧只构造一次累计数组。现场日志同时确认 1.5 m/s 的手动目标受 `1.5 m/s²` 安全加速度门限约束，约 1 秒的升速过程属于既有安全斜坡，未擅自提高门限。

## 2. 控制故障分析

### 2.1 真实现象

- 键盘指令曾短暂到达车辆轮组，说明键盘事件和车辆执行器链路本身可以工作。
- Dashboard 选择遥控器后，RC 一直处于未解锁状态。
- RC worker 持续提交未激活命令，仲裁器随即撤销当前所有者。
- 主循环又依据 Dashboard 下拉框重新选择 RC，形成重复的“选择 RC—撤销 RC”状态切换。
- 键盘输入在 RC 被选择期间不会获得控制权，因此用户看到的是键盘和遥控器同时失效。

### 2.2 根因

旧 RC 安全门禁按常见 SBUS 范围使用约 `1400/1600` 的低、高门限，但当前真实设备的 CH6 两档约为：

| CH6 状态 | 实测值 |
| --- | ---: |
| 低位 | 约 448 |
| 高位 | 约 1002 |

旧门限使 CH6 永远无法到达解锁高位。新门限调整为：

| 参数 | 新值 |
| --- | ---: |
| `unlock_low` | 650 |
| `unlock_high` | 850 |

该门限仍保留滞回区，并要求先观察到低位、再观察到高位，不会因为启动时 CH6 已经处于高位而直接解锁。

### 2.3 修复行为

- RC 使用真实设备范围完成低位到高位解锁。
- RC 未激活时输出保持为零。
- RC 未就绪且 Dashboard 当前选择 RC 时，自动切回键盘。
- Dashboard 明确提示“先将 CH6 拨到低位再拨到高位”。
- 串口、解析器、100 ms watchdog 和 Command IPC 的原有安全归零行为保持不变。

相关实现：

- `slope_sim/serial_rc.py`
- `slope_sim/dashboard.py`
- `tests/unit/test_serial_rc.py`
- `tests/unit/test_dashboard.py`

## 5. 项目整体评估

### 5.1 轻量性

当前源码规模和依赖能力较完整，但开发环境与历史制品偏重。

| 项目 | 当前情况 | 评价 |
| --- | --- | --- |
| `slope_sim/` | 约 16 MB、约 4 万行 Python | 源码体积可接受，但核心模块偏大 |
| `tests/` | 约 22 MB、约 7.6 万行 Python | 覆盖较充分，维护成本较高 |
| `build/` | 约 27 GB | 明显过重 |
| `results/` | 约 3.6 GB | 需要保留策略 |
| `references/` | 约 1.8 GB | 可接受，但应区分必需与参考仓库 |
| Dashboard 图表 | 原先全部创建 | 本次已改为按需加载 |
| Conda 环境 | 同时包含运行、测试和 Jupyter 依赖 | 不适合作为最小运行环境 |

`build/` 中存在多个约 3.4–3.5 GB 的 release 安装根，以及一个约 9 GB 的复现构建根。它们属于已有历史制品，本次没有删除。

### 5.2 可操作性与人性化

已有优点：

- 车型和地形切换需要显式点击“应用”，可以避免误操作立即重建物理世界。
- 键盘、RC 和外部命令统一经过命令仲裁，不允许绕过唯一 C++ Command 发布者。
- Dashboard 能显示当前控制所有者、RC 通道、频率、帧年龄和故障原因。
- 采集、导出和 Viewer 操作集中在同一个 Dashboard。

主要问题：

- PyBullet 与 Dashboard 是两个窗口，新用户容易误解键盘焦点和控制权的关系。
- “已选择控制源”和“实际拥有控制权”是两个状态，原界面提示不够直观。
- RC 解锁需要固定操作顺序，过去没有清晰提示。
- 图表数量多，原布局给用户造成所有信息都必须同时打开的感觉。
- 场景参数改变后还需要点击“应用”，但缺少明显的“有未应用修改”状态。

本次已解决 RC 自动回退、解锁提示和图表按需选择三个问题。

### 5.3 性能

已有合理设计：

- PyBullet 物理步为 240 Hz。
- 轮命令和轮状态目标为 100 Hz。
- LiDAR、RTK 和 IMU 为 10 Hz。
- Dashboard 状态和图表默认刷新为 5 Hz。
- LiDAR 使用独立 worker 和有界通信边界。
- Recorder 队列有界，进程关闭具有升级回收路径。

主要热点：

1. 手动遥测 CSV 仍按 240 Hz 物理步逐行写入。
2. v2 Dashboard 接收快照在每个物理循环前后各刷新一次，入口调用频率最高可接近 480 次/秒。
3. Dashboard、接口 runtime 和 LiDAR worker 单文件均超过 3000 行，热路径和生命周期逻辑集中，后续性能定位成本较高。
4. C++ MCAP Recorder 采用无压缩直写，降低了实时 CPU 抖动，但会增加磁盘占用。

### 5.4 资源管理

日志目录现有约 400 个文件，总体约 1.8 GB。最新车辆 CSV 实测：

```text
4264 行
17.762 秒仿真时间
240.0 行/秒
约 1489.5 字节/行
```

按当前格式估算，连续记录一小时约产生 1.28 GB CSV。对于日常驾驶调试，这一写入量明显过高，也会造成不必要的 SSD 写放大。

进程资源所有权总体清晰：

- Python 主进程拥有 PyBullet、Dashboard 和 v2 runtime。
- C++ Command 独占 wheel command publisher。
- C++ Recorder 独占 MCAP 会话。
- Export 为短生命周期进程。
- ROS Bridge、RViz2 和 Viewer 为可选子进程。
- LiDAR worker 的正常关闭、terminate 和 kill 升级路径已经定义。

因此，当前最明显的资源问题来自日志频率和历史构建制品，而不是缺少进程清理机制。

## 6. 优化方案

### P0：立即执行

本次已完成：

- 修复 RC 解锁门限。
- RC 未就绪时自动恢复键盘。
- Dashboard 图表默认按需创建。
- 取消图表时释放绘图资源和缓存。
- 补充 RC 和图表操作说明。

已完成非 RC GUI smoke：在本机 X11/Intel Mesa OpenGL 会话中以 `--gui --manual --no-interface --duration-sec 2` 启动 PyBullet 与 Dashboard，正常产生日志、图表并关闭。该 smoke 不替代用户对窗口焦点和方向键手感的主观确认。

用户已明确将 RC 实机验收从当前阶段范围移除；RC 解锁、串口 watchdog 与自动回退的自动化回归继续保留，但本阶段不再等待物理遥控器设备。

### P0 补充：正式 v2 Dashboard 状态与点云页

已修复手动 smoke 命令和 Dashboard 的模式混淆：`--no-interface` 只用于不启动 eCAL 的键盘/PyBullet 测试，不能用于实时 MID-360 或 eCAL 验收。该模式现在明确显示“接口已禁用”，不会再把已关闭的接口误报为“等待连接”。

正式 v2 会话的顶层标签只保留一个“接口状态”页，使用 v2 observer 的真实五话题状态；旧接口的前/后双雷达不再伪装为正式状态。连接总览加五个实际话题状态仍提供六个可读状态区块。MID-360 实时点云工作台继续使用原有的当前帧/累计、着色、视角、时间窗与车辆朝向显示，但移动到顶层“LiDAR点云”页，避免与接口状态混在一起。

### P1：优先优化

#### 1. 降低日常 CSV 写入频率

已完成：

- 默认遥测日志为 20 Hz，`telemetry_log_hz: 240` 可显式启用完整诊断采样。
- 物理和控制循环仍保持原频率，只降低落盘采样频率。

默认 20 Hz 时，CSV 写入量约降为原来的十二分之一。文件轮转与保留容量策略仍待单独定义，避免未经确认删除现有会话记录。

#### 2. 合并 v2 Dashboard 刷新入口

已完成：物理循环前后的两次接收刷新已合并为一个独立 UI 节拍，使用现有 `dashboard_update_hz`（默认 5 Hz）。物理、命令和传感器节拍保持不变。

预期效果：减少主线程中的快照复制、文本更新和 Qt 调用，降低 GUI 抖动风险。

#### 3. 建立构建制品保留规则

本轮按以下规则执行：

- 一个当前构建根。
- 一个可复用 canonical cache。
- 一个当前 release 验收安装根。

删除前逐个确认测试、锁文件、交付报告和现有验收脚本是否引用。历史 release、复现构建根和普通运行日志不进入 Git，也不作为当前阶段五源码快照的运行依赖；本轮不构建新的 `.run`，只保留仍被阶段四交付报告引用的 canonical 证据，待遥控器验收后再确定正式版本号和发行制品。

#### 4. 增强控制源状态提示

已完成：Dashboard 已明确区分控制源的三态：

- 未就绪。
- 等待接管。
- 已接管。

RC 未完成低位到高位解锁时，状态区会提示操作顺序，并自动退回键盘；未启用串口时，遥控器选项会移除。

### P2：中期优化

#### 1. 拆分环境

已完成环境分层：

- 最小发行运行环境：冻结在 `packaging/python-environment.yml` 与对应 lock，不含 pytest、Jupyter 或分析工具。
- 源码开发测试环境：`environment.yml`，包含 PyBullet、Dashboard、eCAL、协议生成和 pytest。
- 数据分析环境：`environment-analysis.yml`，只放置 NumPy、pandas、SciPy、MCAP 与 Jupyter，不包含 PyBullet GUI、串口或 eCAL 运行时。
- 构建环境：继续由 C++、安装器和发行相关脚本独立管理。

这样可以减少部署体积，并避免普通运行设备和源码 GUI 开发环境携带 Jupyter 等非运行时组件。

#### 2. 渐进拆分大型模块

不建议一次性重构。本轮核对确认图表规格、遥测历史和接口历史已经位于 `slope_sim/dashboard_charts.py`，因此不为形式上的拆分再移动 Dashboard 生命周期代码。后续修改相关功能时，可逐步提取：

- Dashboard 图表生命周期管理器。
- 控制源和 RC 状态显示组件。
- v2 Dashboard 快照调度器。
- LiDAR worker 生命周期与扫描计算模块。

每次提取都应保持公开行为不变，并使用现有聚焦测试证明等价。

#### 3. 可配置 MCAP 压缩与离线压缩

已完成：实时 Recorder 保持默认无压缩，以避免不可预测的 CPU 抖动。采集完成后，Dashboard 可显式请求“压缩 MCAP（离线）”；主循环在后台线程以 Zstandard 重写为同目录 `session.zstd.mcap`。

- 原始 `session.mcap` 从不覆盖或删除。
- 压缩前会拒绝临时、符号链接或未完成的输入；目标文件已存在时拒绝覆盖。
- 重写保留 MCAP 的 schema、channel、metadata、时间戳、sequence 和原始 protobuf bytes。
- Dashboard 回显原始与压缩后的大小，压缩失败不会影响已验证的 LVX2 或 Viewer 重试。

压缩副本与原始文件可由用户在确认备份需求后自行决定是否归档或删除；本次不自动清理任何会话制品。

### P3：长期可观测性

已完成：开发者诊断页提供 1 Hz 的轻量资源状态区。它通过 Linux `/proc` 显示 Python 主进程、C++ Command 与已启动离线重建子进程的 CPU、RSS 和调度状态；Qt 线程只渲染不可变快照，不直接读取系统状态。

同一低频快照还会显示：

- 物理循环累计超期次数。
- Dashboard 最近两次实际刷新计算出的频率。
- 串口实际帧率、最后帧年龄和 watchdog 失联事件数。
- 当前 CSV 文件增长速率与总大小。
- 当前采集目录的总大小。

这些指标默认不写入高频日志。各 C++ worker 队列目前没有跨进程只读状态合同，因此资源页不会猜测其深度；需要单独定义并验证该 IPC 诊断协议后再接入。

## 7. 人工复测步骤

### 7.1 键盘

1. 启动正式 GUI 会话，并连接当前 SBUS by-id 端口。
2. 保持控制源为“键盘”。
3. 分别在 PyBullet 窗口和 Dashboard 窗口获得焦点时测试方向键。
4. 验证前进、后退、转向和空格停车。
5. 确认 Dashboard 显示当前所有者为键盘。

### 7.2 遥控器

本阶段按用户指示跳过实机遥控器操作。后续恢复该验收时，使用以下步骤：

1. 保持控制源为键盘。
2. 将 CH6 拨到低位，确认状态显示未解锁或 locked。
3. 将 CH6 拨到高位，确认 `unlock=是`。
4. 在 Dashboard 选择“遥控器”。
5. 确认 `source=rc`，再测试前进、后退和转向。
6. 断开串口或停止发送，确认 100 ms watchdog 归零，并自动恢复键盘选择。

### 7.3 图表

1. 启动后确认默认只显示状态、障碍物和模式对应的 LiDAR/v2 页面。
2. 点击右上角“图表（按需）”。
3. 单独勾选轨迹、驱动反馈和 RTK 等图表，确认只出现所选页面。
4. 取消勾选，确认页面立即移除。
5. 反复开启和关闭图表，确认界面无明显卡顿、标签无重复、关闭后不再持续更新对应缓存。

## 8. 剩余风险

- 自动化测试无法代替用户对真实 PyBullet GUI 窗口焦点和车辆运动手感的主观确认；本轮已完成非 RC GUI 启动与正常关闭 smoke。
- 本阶段按用户指示没有连接或采样物理 RC，因此未新增 CH6 低位到高位人工拨动记录。
